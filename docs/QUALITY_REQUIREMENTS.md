# LOM AI — требования к качеству

Определяет качество, проверку и готовность согласованного поведения из [TECHNICAL_REQUIREMENTS.md](TECHNICAL_REQUIREMENTS.md). Это требования к завершённому приложению; фактический статус — в [README](../README.md#этапы-реализации).

## Качество реализации

| Область | Требование |
| --- | --- |
| Типы и состояние | TypeScript strict, discriminated unions и exhaustive-проверки; чистые синхронные reducers, сериализуемый store/actions |
| Асинхронность | Соблюдать runId/terminal guard, отмену и cleanup по [контракту](TECHNICAL_REQUIREMENTS.md#данные-и-события); монтирование UI не запускает run |
| Производительность | Фоновая дельта не перестраивает открытую историю, streaming не мешает чтению; селекторы и scroll — по техническим требованиям |
| Надёжность | Нет вечного loading, смешения чатов и потери вопроса при retry; ошибки локальны, при отказе storage доступна работа в памяти |
| Простота | Существующие модули и локальные ref/state; без новых scroll/delete-сервисов, middleware и абстракций ради потенциального роста |
| Представление | Без исполнения пользовательского HTML и произвольных URL; соблюдать формат сообщений, размеры, фокус и визуальные состояния технических требований |

Базовая доступность: нативные button/textarea, семантические области, видимая подпись, доступные имена, видимый focus и основные действия с клавиатуры. Статусы объясняются текстом, а не только цветом. Dialog/drawer удерживают Tab, закрываются Escape и возвращают focus. У изображения описательный alt; reduced motion — по техническим требованиям. Специализированный аудит не нужен.

Контраст обычного текста/placeholder ≥ 4,5:1, крупного ≥ 3:1 ([W3C](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum)); проектный порог информативных границ/иконок/focus — 3:1. Светлый разделитель не заменяет границу поля. Проверяется итоговый render, это не заявление об аудите.

### Качество учебных ответов

- На этапах 1–3 до использования доступны «Дальше» и конкретный вопрос; после ответа на вопрос только «Дальше»; на четвёртом — оставшиеся вопросы проверки. Без «Объясни подробнее» и «Решить ещё одно уравнение».
- Дополнительный ответ непосредственно объясняет заданный вопрос, не повторяя целиком основной ответ.
- Не объявлять текущий этап, сохранение прогресса или запрет перехода; состояние сохраняется без технических пояснений пользователю.
- Приводить только нужную часть выражения; не повторять полученное равенство без необходимости и не раскрывать будущие преобразования/ответ.
- После успешного пояснения убрать вопрос текущего этапа; ручной повтор, fallback/switch/reload не возвращают его. Ошибка/Stop не расходуют вопрос. Новый этап получает свой набор; после обоих вопросов проверки подсказок нет.
- «Покажи проверку подробнее» раскрывает отдельные вычисления; «Объясни, как проверить ответ» объясняет способ проверки, не дублируя полный разбор.

## Автоматизация

### Unit — Vitest

Изолированно, без всего приложения: reducers/события, форматирование/валидация, mock-контекст/сценарии/калькулятор, JSON/debounce/восстановление и вспомогательные функции. Значимые случаи: двойной send, terminal/runId guard, выбор соседа после delete, ошибочная пара вне контекста, image только по отдельному запросу, сбой storage без перезаписи.

Timeout, исключение, ранний конец итератора, abort-aware delay и cleanup проверяются целевыми unit requestExecutor с заглушками dispatch/getState и управляемым итератором. Использовать [таймеры Vitest](https://vitest.dev/guide/mocking/timers). Без теста каждого тривиального действия и snapshot всего UI.

Учебные проверки: все порядки трёх действий Ньютона, схема сразу после объяснения, fallback/Retry без потери прогресса; четыре этапа нового уравнения, уточнения без продвижения и раннего ответа, корректная подстановка. Подсказки: только последний completed-ответ, обновление/исчезновение, свой чат, reload и исключение неуспешных пар. Отправка подсказки — один run, draft сохранён; устаревший/использованный/недоступный вариант отклоняется. Проверить расходование вопроса только после completed, сброс на следующем этапе, ручной повтор и восстановление без дополнительных записей истории. Поведение DOM/клавиатуры проверяется вручную и единственным E2E ниже.

История действий: фактический порядок analyzed/calculated/image_prepared/answer_composed, последнее действие до completed; незавершённые операции в список не попадают. При сбое сохраняются выполненные действия, успешное завершение запроса не показывается. Одинаковый kind с разными ID сохраняется, повтор actionId не добавляется. Проверить сохранение actions/expanded на переходах и при interrupted, чистый Retry, защиту от поздних событий/устаревшего раскрытия, работу с предыдущим ответом и неизвестным ID. Длительность acceptedAt → finishedAt, округление до 0,1 с/минуты, нулевое/отрицательное значение; без нового UI-таймера. Запись раскрытия немедленная, в том же JSON; восстановление через два store. Старый формат не поддерживается.

Адаптивный streaming: фиксированный random и fake timers; границы диапазонов, один выбор длительности на операцию/блок, два внутренних этапа calculator. Проверить короткий/длинный абзац без потолка 2 с, заголовки/формулы, пункты и паузы; переменные фрагменты/последний остаток, целые surrogate pairs и точное восстановление Markdown/CRLF. Размер фрагмента не меняет суммарное время блока. Отмена операции/выдачи/паузы не оставляет событий или таймеров. Максимальные настройки всех существующих сценариев укладываются в watchdog; случайная вариативность проверяется управляемыми значениями, без вероятностных assertions. Все существующие текстовые сценарии даже на верхних задержках завершаются за ≤ 4 с с полным текстом; calculator < 3 с и быстрее схемы на нижних задержках. Схема готовится 2,5–3,5 с после анализа, завершается без text_delta, пояснения и подписи; полностью пустой ответ по-прежнему отклоняется. С полным объяснением Ньютона её длительность не сравнивается.

Непрочитанное: только успешный completed в фоне ставит отметку своего чата; ошибка/Stop/недопустимое или позднее событие её не создают. Проверить Retry с новым runId, отсутствие отметки после ответа в выбранном чате, снятие при выборе/автовыборе соседа и сохранение через два store без ожидания debounce.

### Integration

Связка Redux → thunk → requestExecutor → mock-agent, isolated store и управляемые задержки/события.

| ID | Сценарий / результат |
| --- | --- |
| INT-01 | Send → streaming → completed: итоговый текст и run корректны |
| INT-02 | Stop → позднее событие: результат остановленного run больше не меняется |
| INT-03 | Switch A → B во время генерации: выбран B, ответ продолжает поступать только в A |
| INT-04 | Retry: новый runId, text/imageSrc очищены, вопрос не дублируется; события старого запуска не влияют |

Другие комбинации ошибок, таймингов и UI не становятся дополнительными integration; отдельной обязательной серии UI-интеграционных тестов нет.

### Playwright — ровно один E2E

E2E-01, один browser/viewport, без размножения по матрице:

1. Открыть приложение с чистым состоянием.
2. Отправить «Объясни второй закон Ньютона», дождаться ответа и трёх подсказок.
3. Набрать черновик, выбрать «Покажи схему» сразу после первого объяснения. Проверить одну новую пару сообщений, сохранённый draft и исчезновение подсказок при active.
4. Проверить placeholder «Создаю изображение…» и начальное/промежуточное/конечное состояние эффекта по дизайну; независимо дождаться эффекта и completed, который сразу сохраняет данные. Ответ содержит только изображение без текстового пояснения/подписи; text_delta нет. Раскрыть статус схемы: фактическая длительность с десятыми секунды и завершённые анализ/подготовка схемы/формирование ответа; оставить раскрытым.
5. Выбрать «Объясни проще», дождаться ответа. Подсказки только у последнего ответа; остаётся «Приведи пример из жизни»; draft сохранён.
6. Перезагрузить страницу. Проверить все три вопроса/ответа, draft и изображение: восстановлены, картинка сразу чёткая, анимация не повторяется. История схемы осталась раскрытой, действия и длительность сохранены. Актуальна только оставшаяся подсказка у последнего ответа.

Stop/retry/switch/delete не добавляются отдельными E2E или ветками этого сценария. Адаптив и reduced motion — вручную. Использовать [ожидания Playwright](https://playwright.dev/docs/test-assertions), не произвольные sleep; подготовка должна позволять увидеть placeholder. Служебные test-кнопки в UI не нужны.

## Готовность к передаче

Сначала исправить смешение чатов, двойные run, потерю вопроса при retry, вечный loading, сломанный мобильный ввод/stop/delete. Локальные ref/state и существующие модули достаточны; новых scroll/delete-сервисов, middleware и абстракций ради роста не добавлять.

Готовность: все AC выполнены; typecheck/lint/unit/integration/E2E/build проходят; нет необработанных ошибок и предупреждений Redux/ключей; README соответствует коду, запуск воспроизводим, опубликованное приложение доступно по ссылке GitHub Pages и проверено вручную. Факты проверок фиксируются после реализации, не выдаются за выполненные сейчас.

Результат: запускаемый репозиторий с lock-файлом, краткий README и доступная демонстрация на GitHub Pages.
